## Compose
### コンテナは1つとは限らない

ここまでイメージをもとにコンテナを作成する流れを見てきました。しかし、実際のアプリケーションが1つのコンテナだけで完結するとは限りません。

例えば、先ほどのGoアプリケーションでデータベースを使用したい場合を考えてみましょう。
まず、PostgreSQLのコンテナを起動します。
```
docker run --name db \
  -e POSTGRES_PASSWORD=password \
  -p 5432:5432 \
  -v app-data:/var/lib/postgresql/data \
  postgres:17
```
つづいて、Goのアプリケーションのコンテナを起動します。
```
docker run --name api \
  -p 8080:8080 \
  my-api
```
さらに、ほかのコンテナを使用したければ、`docker run ....`と何度もコマンドを入力する必要があります。

つまり、起動させたいコンテナを個別に起動する必要があります。さらに、コンテナには以下のような様々な設定があります。

- コンテナ名 : コンテナを識別するための名前
- ポート : ホストOSのポートとコンテナのポートを接続し、コンテナ内のアプリケーションへ外部からアクセスできるようにする設定
- 環境変数 : アプリケーションやコンテナの動作に必要な設定値
- Volume : コンテナから独立したデータの保存領域で、コンテナを削除した際に一緒にデータが削除されるのを防ぐ目的で使用される

よって、コンテナの数が増えるほど、起動時に実行するコマンドや管理する設定も増えていくことになります。

そこで、複数のコンテナをまとめて管理するために、使用するのが次節のDocker Composeです。

### 複数のコンテナをまとめて管理する

Docker Composeでは、複数のコンテナの構成・設定をComposeファイルにまとめて定義することができます。

例えば、アプリケーション全体を以下のように定義します。

```
Compose 
    │
    ├── Go Application 
    │
    ├── PostgreSQL 
    │ 
    └── Redis
```

このようにComposeでまとめることで、複雑な設定をまとめて管理することができます。

### Composeファイルで一括管理

Composeファイルは、一般的に`compose.yml`または、`docker-compose.yml`というファイルに以下のように記述します。

```
services:
  api:
    build: .
    ports:
      - "8080:8080"

  db:
    image: postgres:17
    environment:
      POSTGRES_PASSWORD: password
    ports:
      - "5432:5432"
    volumes:
      - app-data:/var/lib/postgresql/data

volumes:
  app-data:
```

このように、複数のコンテナに必要な設定を1つのComposeファイルにまとめて管理できます。

そして、`docker compose up`というコマンドで、一括でComposeファイルに定義されたサービスをまとめて起動できます。

以上のようにして、Docker Composeを使用することで、これまで個別に実行していたdocker runコマンドを、Composeファイルとしてまとめて管理できるようになります。

## Composeファイルを理解する
### services：管理するサービスを定義する

まず、Docker Composeでは、アプリケーションを構成する複数のコンテナを、それぞれサービスとして定義します。

よって、`services`では、アプリケーションを構成するサービスを定義します。今回は、api・dbという２つです。apiはGoで作成したアプリケーション、dbはPostgreSQLを表しています。
ここで使用しているapiやdbは、任意の名前を付けられます。ただし、サービス名はComposeの中で、そのサービスを識別するために使用されます。そのため、サービスの役割が分かりやすい名前を付けることが一般的です。

重要なことは、単なるコンテナ名ではなく、Composeで管理するサービスを表していることになります。

### build：Dockerfileを使用してイメージを作成する

次に、apiサービスを見てみましょう。

```
api: 
  build: .
```

とあると思います。このとき、`build`は、Dockerfileを使用してイメージを作成するための設定です。ですので、`.`で、ディレクトリを表しているため、DockerfileはComposeファイルと同じディレクトリにあることがわかります。

ただし、buildは単純にDockerfileを実行する設定ではありません。`.` で指定されたディレクトリは、Dockerfileを探す場所であると同時に、Dockerイメージを作成する際のビルドコンテキストにもなります。

そのため、Dockerfileの、`COPY . .`の左側の`.`部分は、このディレクトリ内のファイルを参照できます。

### image：既存のイメージを指定する

一方で、dbサービスでは、buildではなくimageを使用しています。

```
db: 
  image: postgres:17
```

`image`は、使用する既存のDockerイメージを指定するための設定です。ですので、今回設定している`postgres:17`は、PostgreSQLのDockerイメージです。そのため、Dockerfileで自作する必要はありません。

ここで、`build`と`image`の違いを確認します。
- build : Dockerfileを使用してイメージを作成する
- image : 既存のイメージを指定する

---

> なぜ`api`では、`build`を行い。また、`db`では、`image`にするのでしょうか。

まず、`api`で`build`を使用しているのは、自分で作成したGoアプリケーションだからです。GoアプリケーションのソースコードやDockerfileは自分で作成しているため、それらをもとに独自のDockerイメージを作成する必要があります。例えば、自分で作成したGoアプリケーションのイメージをあらかじめDocker Hubなどのレジストリへ公開している場合には、
```
api:
  image: my-user/my-api:1.0
```
のように指定できます。この場合、Composeは既存のイメージを使用します。

一方`db`ですが、もちろん、PostgreSQLについてもDockerfileを作成し、buildを使用することは可能です。しかし、PostgreSQLにはすでに公式イメージが用意されています。特別なカスタマイズが必要ない場合、自分で同じ環境を作成する必要はありません。そのため、既存のイメージを使用します。

つまり、Goアプリケーションはあなたが作成したものであるため、Docker Hubなどのレジストリに公開していない限りは、*オリジナル*なものであるわけです。対して、dbでのイメージはPostgreSQLなどが公開しているものなので、オリジナルなものではないため、イメージを取得し、データベースとして運用するという違いがあるわけです。

---

### ports：ホストとコンテナのポートを接続する

次は、`ports`です。

```
ports: 
  - "8080:8080"
```

ホスト側のポートとコンテナ側のポートを接続するための設定です。形式は、`ホスト側のポート:コンテナ側のポート`です。つまり、ホストOSのlocalhost:8080とコンテナの8080を接続します。

また、PostgreSQLについても同様です。ホストOSの5432番ポートと、PostgreSQLコンテナの5432番ポートを接続できます。

portsは主に、ホストOSや外部からコンテナへアクセスするために使用します。

### environment：コンテナに環境変数を設定する

`environment`は、コンテナ内で使用する環境変数を設定します。

```
environment: 
  POSTGRES_PASSWORD: password
```

例えば、今回使用しているPostgreSQLイメージでは、PostgreSQLを起動するために必要な設定を環境変数として渡せます。環境変数を使用することで、アプリケーションの設定をソースコードの中に直接記述せずに管理できます。ですので、データベースのパスワードや接続先などの設定値を、環境変数として渡すことができます。

※ただし、実際の開発や本番環境では、パスワードをComposeファイルへ直接記述することは注意が必要です。

そのため、.envファイルなどを利用して、以下のように設定してください。
.envファイルで`POSTGRES_PASSWORD=password`と記述します。そして、

```
environment: 
  POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
```

このようにすることで、パスワードなどの設定値をComposeファイルに直接記述せずに管理できます。

### volumes：コンテナの外部にデータを保存する

最後に、`volumes`です。
Dockerの大きなメリットの1つは、コンテナを簡単に作成・削除できることです。しかし、PostgreSQLのデータをコンテナの内部にのみ保存していた場合、コンテナを削除するとデータまで失われる可能性があります。

そのため、コンテナとデータを分離する必要があります。
そこで使用するのが`Volume`です。

今回の設定では、

```
volumes:
  - app-data:/var/lib/postgresql/data
```

としています。ここでは、*このサービスに、どのVolumeを、どこへ接続するのか*を定義しています。

`/var/lib/postgresql/data`は、PostgreSQLがデータを保存する場所です。

そして、例の一番最後に、以下のようにVolumeそのものを定義されているかと思います。

```
volumes:
  app-data:
```

ここでは、*`app-data`という名前のVolumeをCompose全体で定義する*ための設定です。

つまり、今回のComposeファイルには、次の2つのvolumesが登場します。

1. サービス内に、`app-data`をPostgreSQLコンテナのデータ保存場所として使用することを指定
2. `volumes:`で、Docker Volumeである`app-data`を、この場所へ接続しています。

これにより、PostgreSQLのコンテナを削除して新しく作り直した場合でも、同じVolumeを接続することでデータを引き継げます。

### 全体像
Dockerfileでは、主にアプリケーションを実行するためのイメージを作成しました。

一方、Composeでは、アプリケーションを構成する複数のサービスと、それぞれに必要な設定をまとめて管理します。

Docker Composeを使用することで、複数のコンテナを単なる個別のコンテナとしてではなく、1つのアプリケーションを構成するサービス群としてまとめて管理できるようになります。
